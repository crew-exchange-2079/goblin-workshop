# FIX-106 - accept US (0x1f) in names, with round-trip proof

Draft only: **not sent upstream**. Base: upstream main `efc9e3a5c498504c03c2f1d0b931bae058922104`. Patch `fixes/106.patch` (clean `git apply --check`; 2 files, +5/-15). Built like FIX-333 (file backend, root, `/dev/fuse`, no tape hardware).

## Change
- `src/libltfs/pathname.c:442` `_pathname_valid_in_xml`: stop rejecting 0x1f (NUL, surrogates, 0xfffe/0xffff still rejected). Every other control char 0x01-0x1e was already accepted, so 0x1f was the odd one out.
- `src/libltfs/xml_reader_libltfs.c:117-149` `decode_entry_name`: remove 0x1f from the two lists that turned a decoded US into literal text `%1F` / `_`; delete the two TODO comments.
- No writer change needed: `fs_is_percent_encode_required` (`fs.c:195`) already flags 0x00-0x1f and the writer already emits `percentencoded="true"` (`xml_writer_libltfs.c:153`).

## Round-trip test (`fixes/106/repro106.sh <prefix> <unfixed-prefix>`)
Creates a file `aaa<US>aaa` containing "hello", a directory `dir<US>x`, a symlink `lnk<US>y`, and a file with the literal text `lit%1Fz`; unmounts; checks the index on tape; remounts and reads everything back by name.

| | unfixed (`output_before_fix.txt`) | fixed (`output_after_fix.txt`) |
|---|---|---|
| create file / mkdir / symlink | all fail (EINVAL) | all succeed |
| index on tape has `aaa%1F...` | 0 records | 2 records (both partitions) |
| remount + read back | nothing to read: **FAIL** | content "hello", dir and symlink found by their 0x1f names; literal `lit%1Fz` stays distinct: **PASS** |

## Compatibility risk, and what the "historical issue" is
What the repo shows (commits read in the clone): pathname validation has rejected 0x1f since the initial GitHub commit (`c72da04`, 2017). Issue #106 asked to accept it. On the same day the maintainer changed only the **reader** (`de6c39d`, #107): a decoded US is now kept as literal `%1F` text (or `_`) so that indexes written by "bad manner writers" mount instead of failing, with a TODO saying US should really be accepted and that it is rejected "because of a historical issue". **The reason itself is not written down anywhere I could read** (no commit body, no doc, issue thread unread). So I cannot say why 0x1f was excluded originally; treat that as unknown and ask a maintainer.

Observed impact (informational part of the test, run on the file backend):
1. **Old LTFS reading a tape with a US name**: still mounts (no failure), shows names as literal `aaa%1Faaa`.
2. **Old LTFS rewriting the index of such a tape** (any change then unmount) silently renames those entries to the literal `aaa%1Faaa`; the fixed build afterwards sees the literal names (shown in `output_after_fix.txt`, section 3). Data is intact, names are not. This is the real compatibility cost: mixed old/new LTFS versions on the same tape lose the 0x1f in names.
3. **Existing tapes written by other writers with `%1f` entries**: today they appear with literal `%1F` names and get rewritten as `%251F` on the next index write; with the fix they appear with a real 0x1f and keep it. Visible names change on mount, tape contents are untouched.
4. **No change** to tape format, to tapes without 0x1f names, or to names that merely contain the text `%1F` (tested).
5. **Not tested / unknown**: other LTFS implementations (Windows/macOS ports, IBM tools), format-spec text on allowed characters (not read), `ltfs_ordered_copy` and `filename_handling.c` (which already replaces 0x01-0x1f with `_` for Windows-safe names), xattr names / symlink targets / volume names that share `_pathname_valid_in_xml`, raw (non-encoded) 0x1f in XML, which XML 1.0 forbids and libxml2 should reject (not changed, not tested).

Recommendation: do not send without a maintainer answer on the original reason and on whether a mixed-version rename is acceptable. A conservative alternative is to accept 0x1f only at creation and keep the reader as is (new tapes would then read back as literal `%1F` on all versions, which defeats the round trip), so I did not pursue it.
