# FIX-333 - index-cache write failure must not lose the index on tape

Draft only: **not sent upstream** (no comments/PRs/pushes to LinearTapeFileSystem). Base: upstream main `efc9e3a5c498504c03c2f1d0b931bae058922104`. Patch: `fixes/333.patch` (`git apply --check` clean on a pristine clone; 2 files, +15/-12).
Build: autogen + `./configure --disable-snmp` + make on Ubuntu 24.04 (apt: libfuse-dev libxml2-dev libicu-dev uuid-dev libsnmp-dev autotools). uthash submodule fetched at the pinned commit 2031adf from github.com/troydhanson/uthash (clone has no submodule content). The 5 build warnings are outside `xml_writer*.c`.

## Important scoping finding
Upstream never assigns `vol->index_cache_path` (only freed: `ltfs.c:473-474`; declared `ltfs.h:402`). It is a hook for external code (the cache/offset-cache code mentions `.LTFSEE_DATA`). So **stock `ltfs`/`mkltfs` never reach the failing code**; the bug only bites programs that set the field. My test sets it with an LD_PRELOAD shim. That lowers user impact and may affect acceptance: upstream may see the fix as relevant only to external consumers.

## Root cause
`xml_output_tape_write_callback` (`xml_writer.c:108,123-129`) returned -1 when the cache `arch_write` failed (and on every later call because of the `errno_fd` check), so libxml2 stopped emitting. The close callback (`:158-170`) skipped the final tape block and returned -1 likewise. `xml_schema_to_tape` (`xml_writer_libltfs.c:894-897`) then treated a cache error like a tape error: no trailing filemark, rollback of generation/pointers in `ltfs_write_index` (`ltfs.c:2624-2635`), error to the caller. Result: a recoverable side-file error truncated the index on tape and failed mkltfs/unmount.

## Fix (smallest design that matches the issue text)
Per the issue's expected behavior ("write entire index to the tape even if cache write fails, report the error after"):
- Callbacks: a cache write error records `errno_fd` (already logged as 17244E/17245E/17206E), stops further cache writes, but keeps writing tape blocks. A cache fsync failure is recorded too instead of returning -1.
- `xml_schema_to_tape`: only a tape error (`err_code`) takes the failure path. On a cache error the filemark is still written, the previous cache contents are restored (`xml_release_file_lock(..., revert=true)`), and `_commit_offset_caches` is skipped. The function returns the tape result (0), so generation/pointers stay consistent with what is on tape.
- Design choice for a maintainer: the cache error is reported by the existing ERR log lines only. Returning the error after the filemark would make `ltfs_write_index` roll back its in-memory generation although the index is already on tape, so I did not do that.

## Test (file backend, no hardware)
`fixes/333/repro333.sh <prefix> <shim.so>` with `fixes/333/cache_fault.c` (shim sets `index_cache_path` from `$LTFS_FI_CACHE` and fails writes to that file with ENOSPC; `LTFS_FI_OFF=1` disables the failure). Scenario A: `mkltfs -b 4096` (close-callback path), then remount. Scenario B: mount, create 60 files, unmount (index spans several 4 KiB blocks, so the write-callback path at `:123-129`; the cache is only used for the index-partition write).

## Risk to existing tapes
- Tape format unchanged; the same index bytes are written. Only the failure path changes: an index that used to be left without trailing filemark is now complete.
- Behavior change for cache users: a cache error no longer fails the index write, so a consumer relying on the error return to learn the cache is stale will not see one (the cache is restored to its previous contents, which is stale by one generation). Needs a maintainer decision.
- Not tested: real tape backends, LTFS-EE, concurrent cache readers/locks, ENOSPC mid-way through larger indexes beyond scenario B, the `fd > 0` vs `>= 0` inconsistency at `xml_writer.c:130` (left untouched), the pre-existing wrong variable in the 17061E message. Only the file backend was exercised; nothing about physical drives is claimed.
